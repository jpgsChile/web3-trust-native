# CDR-004 — Eliminación de `source.authority` del Contrato de Manifest

| Campo | Valor |
|-------|--------|
| ID | CDR-004 |
| Título | Eliminación de `source.authority` del Contrato Semántico de `manifest.json` |
| Estado | **ACCEPTED** |
| Fecha | 2026-08-25 |
| Dependencias | CDR-001, CDR-003 (CDR-002: contexto L7/L8; sin cambio de identidad) |
| Origen | Decisión humana preliminar (custodio) — formalización como propuesta |
| Implementación | **Ninguna** en este CDR: no modifica manifests, reglas, hooks ni Git |

---

## 1. Contexto

La auditoría C1 (solo lectura) confirmó que los diez `constitution/*/manifest.json` declaran:

```json
"source": {
  "authority": "git"
}
```

mientras el repositorio **no** contiene `.git`.

CDR-001 ya fija las **superficies de autoridad normativa** (Constitución / `constitution/` / STANDARD / operativo / histórico).  
CDR-003 fija que **Git no crea autoridad**; solo **preserva** textos y decisiones ya adoptados, y que `manifest.authority: git` es **prematuro** hoy.

El campo `source.authority` en el contrato de manifest (`manifest-contract.mdc`, hook `after-edit-manifest-validate.py`) introduce una etiqueta machine-readable que un agente puede leer como **segunda superficie de autoridad**, mezclando:

- autoridad **normativa** (qué texto obliga), y  
- **preservación** / trazabilidad de repositorio (cómo se versiona el árbol).

---

## 2. Problema

1. **Ambigüedad semántica:** ¿`authority` significa “quién legisla”, “dónde está la fuente oficial del Libro”, o “mecanismo de preservación”?  
2. **Inconsistencia factual:** valor `"git"` con Git **ausente**.  
3. **Segunda superficie:** CDR-001 ya mapó autoridad; un campo homónimo en metadatos invita a tratar el manifest como árbitro normativo.  
4. **Validación falsa:** el hook exige la clave pero no valida existencia de `.git` ni enum cerrado → “manifest OK” con declaración falsa de preservación.  
5. **Bloqueo de C2:** materializar CDR-003 en manifests sin decidir este campo perpetúa o agrava la contradicción.

---

## 3. Evidencia (C1 + CDR previos)

| Fuente | Hecho |
|--------|--------|
| 10 manifests | `source.authority: "git"` |
| `.git` | Ausente |
| `manifest-contract.mdc` | Exige `authority` (`git` cuando aplique) |
| `after-edit-manifest-validate.py` | `SOURCE_REQUIRED` incluye `authority` (solo presencia) |
| CDR-001 | Manifest = metadatos auxiliares; **no** legisla |
| CDR-003 §12 | Git = preservación; `authority: git` prematuro |
| AUTHORITY-MAP / FORBIDDEN-ACTIONS (Lote B) | No afirmar `authority: git` efectivo sin `.git` |
| C1 HR-C1-1 | Semántica de `authority` marcada **HUMAN REVIEW** |

---

## 4. Decisión humana preliminar (entrada de este CDR)

> Proponer la **eliminación** de `source.authority` del **contrato semántico** de `manifest.json`.

**Fundamento declarado por el custodio:**

- CDR-001 ya establece la autoridad normativa;  
- CDR-003 establece Git como preservación futura;  
- `source.authority` mezcla autoridad normativa con preservación;  
- `"git"` es inconsistente con la ausencia de `.git`;  
- mantener el campo crea una posible **segunda superficie de autoridad**.

Este CDR **no** ejecuta la eliminación; la **analiza**, la **compara** con alternativas y la **formaliza como propuesta** sujeta a aceptación humana.

---

## 5. Alternativas consideradas

### Alt-A — Eliminar `source.authority` del contrato (propuesta preliminar)

| Aspecto | Evaluación |
|---------|------------|
| Alineación CDR-001 | Alta: authority vive fuera del manifest |
| Alineación CDR-003 | Alta: Git = preservación futura, no campo de autoridad |
| Consistencia factual hoy | Alta: desaparece la mentira `"git"` |
| Coste de migración C2 | Medio: quitar clave de 10 JSON + contrato + hook + refs |
| Riesgo residual | Bajo si se documenta dónde vive la preservación (existencia de `.git` / release futuro) |

**Veredicto tentativo:** **preferida** como propuesta formal.

### Alt-B — Conservar el campo; cambiar el valor (p. ej. `none`, `absent`, `pending`, `filesystem`)

| Aspecto | Evaluación |
|---------|------------|
| Arregla inconsistencia factual | Parcial (si el valor refleja “sin Git”) |
| Elimina ambigüedad “autoridad” | **No** — el nombre sigue sugiriendo autoridad |
| Segunda superficie | **Permanece** |
| Inventario de enum | Requiere decisión humana de léxico (riesgo de invención) |

**Veredicto:** **no preferida** — mitiga el síntoma, no la confusión categorial.

### Alt-C — Renombrar a `source.preservation` (o `repositoryPreservation`) con valores tipados

| Aspecto | Evaluación |
|---------|------------|
| Separa norma vs preservación | Mejor que Alt-B |
| Alineación CDR-003 | Buena si valores = `none` \| `git` (solo si `.git` existe) \| `release-tag`… |
| Coste | Alto (rename + enum + validación cruzada con disco) |
| ¿Necesario ahora? | Discutible: la preservación puede inferirse de la presencia de Git/release sin campo por Libro |

**Veredicto:** **alternativa válida diferida** — útil si más adelante se necesita metadata de preservación **por Libro**; no obligatoria para cerrar la contradicción actual.

### Alt-D — Conservar `authority: "git"` y crear Git de inmediato

| Aspecto | Evaluación |
|---------|------------|
| Arregla factual | Solo si se inicializa Git |
| Crea autoridad normativa | **No** (CDR-003) — pero refuerza la lectura errónea del campo |
| Mandato | Git sigue **fuera** de lotes no autorizados; no es prerrequisito de este CDR |

**Veredicto:** **rechazada** como solución al problema semántico; Git es decisión de implementación separada.

### Alt-E — Mover “authority” a otro artefacto (`STANDARD`, `releases/`, Carta)

| Aspecto | Evaluación |
|---------|------------|
| Evita segunda superficie en manifest | Sí |
| Solapa CDR-001 | Riesgo de reintroducir ambigüedad si se etiqueta mal |

**Veredicto:** **innecesaria** si Alt-A se adopta: CDR-001 ya es el mapa; no hace falta un campo espejo.

---

## 6. Consecuencias de adoptar Alt-A

### 6.1 Contrato semántico

- `source` pasaría a exigir, como mínimo: `official`, `historical`, y (según taxonomía de migración) `migration` cuando aplique.  
- `authority` **dejaría de ser** campo reconocido del contrato.  
- Presencia residual del campo en disco, tras Accepted, se trataría como **legado no semántico** hasta limpieza C2 (o se elimina en el mismo lote de manifests).

### 6.2 Autoridad normativa (CDR-001)

- **Sin pérdida:** la autoridad sigue en Constitución / árbol / estados de migración-publicación.  
- **Ganancia:** el manifest no puede interpretarse como declarador de autoridad.

### 6.3 Preservación (CDR-003)

- Git / tags / `repositoryRelease` siguen siendo el plano de preservación **cuando existan**.  
- La ausencia de campo no impide documentar en STANDARD/versioning: “preservación = Git cuando `.git` exista”.

### 6.4 Artefactos operativos afectados (post-Accepted; **no** en este archivo)

| Artefacto | Impacto esperado |
|-----------|------------------|
| `constitution/*/manifest.json` | Eliminar clave `source.authority` (lote C2 u otro mandato) |
| `.cursor/rules/constitution/manifest-contract.mdc` | Quitar requisito de `authority` |
| `.cursor/hooks/after-edit-manifest-validate.py` | Quitar `authority` de `SOURCE_REQUIRED` |
| `.cursor/references/*` (AUTHORITY-MAP, FORBIDDEN, etc.) | Actualizar menciones a `authority: git` |
| CDR-003 §12 fila `manifest.authority: git` | Nota de supersesión / alineación tras Accepted |

### 6.5 Lo que este CDR **no** autoriza

- Modificar manifests ahora.  
- Inicializar Git.  
- Inventar `VERSION.md`, releases o `constitutionalVersion`.  
- Alterar L0 / títulos L7–L8 / `dependsOn`.  
- Confundir ACCEPTED documental con materialización completa en disco.

## 8. Decisión (Accepted)

Quedando este CDR **ACCEPTED**:

1. **Eliminar** `source.authority` del **contrato semántico** de `manifest.json`.  
2. Declarar que **ningún** campo del manifest representa autoridad normativa.  
3. Declarar que la **preservación** por Git/release **no** se modela como `source.authority`.  
4. Diferir a decisión posterior (opcional) un campo de preservación tipado (`source.preservation` u homólogo) **solo** si hay necesidad operativa demostrada.  
5. La materialización en disco (JSON, rules, hooks, refs) requiere **lote de implementación** explícito; este CDR por sí solo no edita el árbol de Libros.

---

## 9. Criterios de aceptación (cumplidos)

Este CDR quedó **ACCEPTED** tras confirmación humana de que:

1. Se adopta Alt-A (eliminación) frente a Alt-B/C/D/E, o se documenta otra elección explícita.  
2. Queda claro que manifests **no** son superficie de autoridad normativa.  
3. Queda claro que Git sigue siendo preservación futura (CDR-003), no requisito de este CDR.  
4. Se autoriza por separado el lote que limpie manifests/contrato/hooks (p. ej. C2 acotado).  
5. Hasta el lote de implementación, los manifests pueden seguir conteniendo `authority: "git"` como **legado factual**; los agentes deben seguir las refs Lote B (no tratarlo como efectivo).

---

## 10. Estado

**ACCEPTED** — aceptación humana documental materializada (2026-08-25).

**Manifests: no modificados por este CDR.**
