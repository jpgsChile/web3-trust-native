---

## 1. Contexto

El repositorio presenta números de versión y estados **incompatibles entre sí**, sin mecanismo de publicación ni preservación Git.

`STANDARD.md` ya declara **planos independientes de versionado**, pero el árbol físico no los materializa de forma coherente: coexisten afirmaciones `1.0.0` / `Official` con Libros `0.1.0` `Draft`, L0 `pending-human-review`, stubs L1–L8, y ausencia total de `.git`, `releases/`, `VERSION.md` y `CHANGELOG.md`.

Este CDR responde: **qué significa “versión”** en Web3 Trust-Native y cómo separar versión, estado de migración, estado de decisión y publicación.

---

## 2. Problema

1. El mismo token `1.0.0` o `0.1.0` se usa para objetos distintos (Carta, Architecture, Standard, Libros).  
2. “Estado” mezcla Draft / Official / Fundacional / pending-human-review / Especificación Oficial.  
3. `manifest.source.authority: "git"` aparece **sin** repositorio Git.  
4. Docs raíz citan `VERSION.md` / `CHANGELOG.md` **inexistentes**.  
5. Sin releases/tags, no hay cita pública reproducible.  
6. Riesgo: tratar `1.0.0` como Constitución publicada cuando la autoridad efectiva (CDR-001) aún no lo respalda.

## 5. Modelo conceptual de versiones

### ¿Qué significa “versión” aquí?

En Web3 Trust-Native, “versión” no es un único número de producto. Es un **identificador de revisión** de un **plano** concreto del estándar, independiente del **estado** (migración, decisión, publicación).

### Dimensiones: ¿separar?

| Dimensión | ¿Separar? | Motivo |
|-----------|-----------|--------|
| 1. Versión constitucional del ecosistema | **Sí** | `STANDARD.md` ya la define como “versión **publicada** de la Constitución” |
| 2. Versión individual de cada Libro | **Sí** | Manifests ya tienen `version` por Libro; evolucionan a distinto ritmo |
| 3. Versión del Standard | **Sí** | Ya existe (`0.1.0 Draft`) y gobierna proceso (CDR-001) |
| 4. Versión del repositorio | **Sí (ligera)** | Identifica snapshot del árbol; ≠ norma |
| 5. Versión de publicación / release | **Sí** | Acto de publicación inmutable (tag/release), no el working tree |
| 6. “Versión de migración” | **No como semver** | Es **estado de migración**, no número |
| 7. Estado de madurez | **Sí, como estado** | No como `MAJOR.MINOR` |
| 8. Release/tag | **Sí** | Mecanismo de publicación/preservación |

**Regla:** no mezclar semver con estados (`Draft`, `pending-human-review`, `Official`).

## 6. Estados del ciclo de vida (taxonomía)

Tres taxonomías **disjuntas**:

### A) Estado de decisión (CDR / gobernanza)

| Estado | Significado |
|--------|-------------|
| `PROPOSED` | Borrador de decisión |
| `UNDER_REVIEW` | En revisión humana |
| `ACCEPTED` | Decisión adoptada (aún puede faltar materializar) |
| `REJECTED` | Rechazada |
| `SUPERSEDED` | Reemplazada por otro CDR |
| `ARCHIVED` | Conservada sin efecto operativo |

*(No usar estos estados como `manifest.version`.)*

### B) Estado de migración (Libro) — alineado a `MIGRATION-STATES.md`

| Estado | Significado |
|--------|-------------|
| `historical-only` | Cuerpo solo en `original/*` |
| `draft-migrated` / `pending-human-review` | BOOK borrador; autoridad de trabajo (CDR-001) |
| `human-reviewed` | Fidelidad revisada humanamente |
| `migration-official` | BOOK cerrado como fuente normativa del Libro *(nombre interno; no confundir con release del ecosistema)* |

### C) Estado de publicación (artefacto o release)

| Estado | Significado |
|--------|-------------|
| `UNPUBLISHED` | Solo working tree / sin tag de publicación |
| `DRAFT` | Publicado como borrador citables (si se decide publicar drafts) |
| `OFFICIAL` | Publicación oficial inmutable |
| `DEPRECATED` | Vigente pero desaconsejada |
| `SUPERSEDED` | Reemplazada por otra publicación |

### Versión semántica (número)

Formato propuesto: `MAJOR.MINOR.PATCH` **por plano**, sin embeber la palabra Draft en el número.

- El calificador `Draft` / `Official` vive en el **estado de publicación**, no dentro del semver.  
- Ejemplo correcto: `standardVersion = 0.1.0` + `publicationStatus = DRAFT`.  
- Ejemplo incorrecto como única verdad: “somos 1.0.0” sin estado ni plano.

## 7. Versionado constitucional (`constitutionalVersion`)

| Aspecto | Determinación |
|---------|----------------|
| Qué versiona | El **conjunto normativo publicado** de la Constitución (Libros en estado efectivo publicado), no un archivo raíz aislado |
| Quién la declara | Publicación oficial del estándar (proceso STANDARD), nunca solo un encabezado de `CONSTITUTION.md` |
| Relación con Libros | Puede avanzar cuando el **paquete** constitucional publicado cambia; no exige que todos los Libros tengan el mismo `bookVersion` |
| Hoy | **No hay** `constitutionalVersion` publicada demostrable; el `1.0.0` de Carta/Readme **no** califica |

Definición operacional:  
`constitutionalVersion` = versión del **release constitucional** (paquete de Libros + estados), no el número decorativo de un Markdown raíz.

---

## 8. Versionado de Libros (`bookVersion`)

| Aspecto | Determinación |
|---------|----------------|
| Dónde | `manifest.json` → `version` (ya existe) |
| Qué | Revisión del contenido normativo de ese Libro |
| Independencia | Un Libro puede ser `0.2.0` mientras otro sigue `0.1.0` |
| Acompañamiento obligatorio | `status` (p. ej. Draft) + `source.migration` |
| Hoy | Todos en `0.1.0` Draft; coherente entre Libros; **incoherente** con `1.0.0` raíz |

Bajo CDR-001: `bookVersion` **no implica** norma publicada; la efectividad depende del estado de migración/publicación.

---

## 9. Versionado del Standard (`standardVersion`)

| Aspecto | Determinación |
|---------|----------------|
| Dónde | `STANDARD.md` (hoy `0.1.0 Draft`) |
| Qué | Evolución del marco procesal/organizativo (CDR-001: subordinado) |
| Independencia | Puede subir sin cambiar artículos |
| Límite | No redefine norma (CDR-001) |

Este plano **ya está justificado** por `STANDARD.md` y es necesario.

---

## 10. Versionado del repositorio (`repositoryVersion` / snapshot)

| Aspecto | Determinación |
|---------|----------------|
| Qué | Identificador del árbol de archivos (materialización), no de la norma |
| Forma | Tag Git / release id / commit SHA |
| Autoridad | **Ninguna normativa** (CDR-001: Git preserva) |
| Relación | Un `repositoryVersion` puede contener drafts; solo algunos tags son `OFFICIAL` |

Metaespecificación (`Repository Architecture`) debería llevar `metaSpecVersion` propia (plano ya citado en STANDARD), **no** llamarse “1.0.0 Oficial” mientras describe fantasmas.

---

## 11. Publicación y releases

Publicación ≠ existencia de archivo.

| Elemento | Rol |
|----------|-----|
| Working tree | Trabajo |
| Release/tag | Instantánea **citable** |
| `publicationStatus` | DRAFT / OFFICIAL / DEPRECATED / SUPERSEDED |
| Notas de release | Qué planos y `bookVersion`s incluye; CDRs Accepted incorporados |

**Regla:** un release `OFFICIAL` del ecosistema exige, como mínimo, declaración explícita de `constitutionalVersion` y de los Libros incluidos con su estado de migración/publicación — no un simple bump a `1.0.0` en un README.

---

## 12. Git

| Pregunta | Determinación |
|----------|----------------|
| ¿Git crea autoridad? | **No.** Solo **preserva** decisiones y textos ya adoptados (alineado a CDR-001 y Architecture: independencia de Git). |
| ¿Cuándo crear Git? | Tras mandato humano de implementación; idealmente con política de qué entra en el primer commit. |
| ¿Qué debe representar el primer commit? | Snapshot **honesto**: árbol real + estados Draft + CDRs Accepted + **sin** pretender `constitutionalVersion 1.0.0` publicada. |
| Tags | `draft/*` o `v0.1.0-draft` vs `official/constitutional-x.y.z` — el tag no convierte norma por magia; registra publicación. |
| `manifest.authority: git` | Hoy **premature**; válido solo cuando exista preservación Git real. |

**La materialización de este CDR no inicializa Git.**

| Principio CDR-001 | Cómo lo refleja CDR-003 |

| Autoridad estructural vs efectiva | `bookVersion` ≠ efectividad; estados de migración/publicación deciden |

| Fidelidad | Subir versión oficial de Libro exige migración cerrada, no solo bump |

## 15. Alternativas

### Alt-1 — Un solo semver global para todo
- Simple.  
- **Rechazada:** mezcla Standard, Libros, Carta y repo; contradice `STANDARD.md`; fuerza bumps falsos.

### Alt-2 — Solo versionar Libros; ignorar Standard/repo
- Insuficiente para publicación y gobernanza.  
- **Rechazada** como modelo completo.

### Alt-3 — Planos independientes (Constitucional / Libro / Standard / Meta / Tooling / Release) + estados disjuntos  
- Alineada a `STANDARD.md`.  
- Coste: disciplina de etiquetado.  
- **Necesaria** en lo esencial.

### Alt-4 — Simplificación pragmática de Alt-3 (adoptada)

Mantener planos **mínimos obligatorios**:

1. `bookVersion` + estados de migración (ya parcialmente existen)  
2. `standardVersion` + publicationStatus  
3. `constitutionalVersion` **solo cuando haya release constitucional**  
4. `repositoryRelease` (tag/commit) como preservación  

Tooling/metaSpec versionan cuando existan artefactos reales; no inventar números hoy.

---

## 16. Decisión

1. **Adoptar** el modelo de **planos separados** (necesario; ya enunciado en `STANDARD.md`).  
2. **Simplificar** la operativa a: Libro · Standard · Constitucional(publicada) · Release de repo.  
3. **Separar** semver de estados (decisión / migración / publicación).  
4. Declarar el `1.0.0` actual de Carta/Readme/Architecture como **no válido** como publicación constitucional hasta que existan criterios de release.  
5. Tratar `0.1.0` + Draft en Standard y Libros como la **línea honesta** del estado actual.  
6. Git: preservación posterior; primer commit = Draft honesto, no `1.0.0` oficial.  
7. La materialización de este archivo no modifica números en el árbol ni inicializa Git.

---

## 17. Criterios de aceptación

Este CDR fue aceptado humanamente al confirmarse que:

1. “Versión” se entiende **por plano**, no como un único número de producto.  
2. Existen al menos los planos: `bookVersion`, `standardVersion`, `constitutionalVersion` (solo al publicar), `repositoryRelease`.  
3. Estados de **decisión**, **migración** y **publicación** están separados del semver.  
4. Afirmar `constitutionalVersion = 1.0.0` **hoy** se considera **inválido** como hecho de publicación.  
5. Git **no** crea autoridad normativa; solo preserva.  
6. El primer Git/tag futuro no podrá etiquetarse como Constitución `1.0.0` Official sin Libros en estado de publicación compatible y mandato humano.  
7. Queda alineado con CDR-001 (efectividad) y CDR-002 (identidad L7/L8).
